# PRD --- Java Backend MCP Server

> 项目名称：`java-backend-mcp`\
> Tagline：**Engineering Intelligence for Java Developers**\
> 当前文档版本：Draft 0.1\
> 状态：基于需求访谈形成，进入技术方案细化前的基线版本

## 1. 产品概述

### 1.1 一句话定位

一个面向 Java 后端开发者的 MCP Server，为 Codex、Claude Code 等 AI
Coding Agent 提供可解释、可验证、有证据支撑的 Java 工程分析能力。

### 1.2 产品愿景

让 AI Coding Agent 不只是读取 Java
项目的文件或泛泛回答代码问题，而是能够逐步理解一个真实 Java 后端工程的：

-   项目结构与技术栈；
-   Maven 模块及依赖关系；
-   Spring Boot 配置、组件和 Bean 关系；
-   Controller、Service、Mapper 等代码关系；
-   MyBatis Mapper 与 SQL；
-   代码变更可能影响的模块、接口和业务路径。

同时，为开发者提供日常工程诊断能力，帮助定位依赖冲突、配置风险、Mapper
映射问题和 SQL 风险。

### 1.3 产品不做什么

-   不重新实现通用 Coding Agent，不与 Codex/Claude Code
    竞争代码生成能力。
-   不在 MCP Server 内置大语言模型，不负责自主规划复杂任务。
-   不自行实现 MCP JSON-RPC 协议，优先使用 Spring AI MCP。
-   不把静态分析推断包装成确定的运行时事实。
-   V0.1 不修改目标项目文件，不执行任意 SQL，不执行 DDL/DML。
-   不以 MCP Tool 数量作为产品质量指标。

## 2. 目标与优先级

用户明确的目标优先级：

1.  **开源影响力**：项目要解决真实开发问题，具备清晰差异化，并让开发者愿意使用、反馈和贡献。
2.  **学习成长**：通过产品设计、工程实现、测试和发布深入掌握 MCP 与 Java
    工程分析。
3.  **简历竞争力**：体现系统设计、静态分析、工程质量和 AI
    工具集成能力，但不以简历包装牺牲产品价值。

开源发布目标： - 首发达到可供开发者真实使用的程度； -
建立社区协作基础； - 长期发展为可扩展的 Java
后端工程分析工具，探索分析器/规则插件生态。

## 3. 目标用户与核心场景

### 3.1 核心用户

-   正在开发、维护 Java 后端项目的开发者；
-   刚加入团队、需要快速熟悉成熟 Java 项目的实习生或新成员；
-   使用 Codex、Claude Code 等 Coding Agent，希望 Agent 更准确理解 Java
    工程的开发者。

基础学习者不是首要目标用户。

### 3.2 场景一：陌生项目快速理解

开发者拿到一个规模较大、历史较长的 Spring Boot 项目，希望快速回答：

-   项目由哪些模块组成，采用什么技术栈？
-   项目入口、配置文件和关键组件在哪里？
-   Maven 模块之间如何依赖？
-   Spring Bean、Controller、Service、Mapper 之间有什么关系？
-   某个接口的调用链经过哪些类和方法？
-   修改某个类或方法，可能影响哪些接口和模块？

这是项目的长期核心场景。V0.1
先建立项目画像和基础模块关系，后续逐步扩展调用链和影响分析。

### 3.3 场景二：日常工程诊断

开发者在项目开发中希望快速定位：

-   Maven 依赖冲突、重复依赖和传递依赖来源；
-   Spring Boot 配置、组件扫描和 Bean 依赖风险；
-   MyBatis Mapper 接口与 XML 映射问题；
-   SQL 中潜在的全表扫描、分页和查询条件风险。

### 3.4 典型使用方式

用户在 MCP Client 中提出自然语言任务，例如：

> 帮我了解这个项目的整体结构，找出主要模块和技术栈，并说明模块之间的依赖关系。

或：

> 检查这个项目的 Maven 依赖冲突，给出冲突版本、传递依赖路径和对应
> pom.xml 证据。

MCP Server 返回结构化分析结果和证据；由外部 Agent
负责结合结果进行进一步推理、组织说明或规划后续工具调用。

## 4. 产品差异化与设计原则

### 4.1 三项核心竞争力

**A. 分析深度**

从文件枚举和关键词扫描逐步走向项目结构、模块依赖、Bean
关系、方法调用链和影响范围分析。

**B. 证据可信**

每条重要结论尽可能附带可复核证据，例如： - 文件路径和行号； - Maven
依赖路径； - 配置项及来源文件； - Mapper/XML 对应关系； - SQL
片段及解析位置； - 分析规则和推断依据。

**C. Java 后端专业性**

围绕 Spring Boot、Maven、MyBatis/MySQL，并在后续版本扩展
Redis、RabbitMQ、事务、并发和日志异常等后端工程领域。

Agent 协作能力是重要设计要求，但不是首要卖点。工具接口应便于 Agent
分阶段探索、组合调用和追踪证据。

### 4.2 统一原则

1.  确定性任务交给 Java 分析引擎；LLM 推理由 MCP Client 完成。
2.  结论必须区分事实、规则命中和风险推断。
3.  能给证据就给证据；不能定位时明确说明，不伪造文件、行号或调用关系。
4.  静态分析结果说明覆盖范围和局限。
5.  分析器与 MCP 协议适配层解耦。
6.  先只读、安全、可验证，再考虑更高权限能力。

## 5. 版本范围

工具数量不预先固定。以可独立验收的用户场景和分析质量为依据，不为凑数量拆分
Tool。

### 5.1 V0.1：可用的首发版本

V0.1 同时推进"项目理解"和"工程诊断"两条线，但严格控制每项能力的深度。

#### 项目理解线

-   识别 Maven 单模块/多模块项目结构；
-   识别常见 Java/Spring Boot 技术栈及关键依赖；
-   定位启动类、主要配置文件和关键工程入口；
-   提取模块间 Maven 依赖关系；
-   返回结构化项目画像和模块关系数据。

V0.1 不承诺完整还原业务调用链或变更影响范围。

#### 工程诊断线

-   Spring
    Boot：识别配置文件、关键配置项和常见配置风险；在可行范围内分析组件扫描和
    Bean 关系。
-   Maven：分析依赖树、版本仲裁结果、重复/冲突依赖和传递依赖路径。
-   MyBatis/MySQL：识别 Mapper 接口与 XML 对应关系，提取
    SQL，并实现一组经过测试的基础 SQL 风险规则。

具体规则应在技术设计和 benchmark
样例中进一步确认，不以规则数量作为目标。

#### V0.1 基础产品能力

-   Spring AI MCP Server；
-   STDIO Transport；
-   面向本地授权 Workspace 的只读访问；
-   统一结构化结果模型；
-   输入校验、错误分类和敏感信息脱敏；
-   单元测试、集成测试、真实项目样例、准确性验证和性能基准；
-   GitHub Actions CI；
-   安装、配置、Codex/Claude Code 接入和使用文档。

### 5.2 V0.2：关系分析增强

候选范围： - 更完整的 Maven 模块和 Spring Bean 依赖关系； - 局部
Controller → Service → Mapper 调用链； - 更深入的 Spring
自动配置分析； - Redis、RabbitMQ 工程诊断； - 事务与并发风险分析； -
日志与异常分析的基础能力。

### 5.3 V0.3：调用链与影响分析

候选范围： - 更完整的静态方法调用关系； -
从接口入口追踪关键业务调用链； -
基于类、方法和模块关系进行变更影响分析； -
结果中标记动态分派、反射、代理、异步和跨服务调用造成的分析盲区。

### 5.4 V1.0 及长期方向

-   稳定的规则/分析器扩展机制；
-   MCP Resources、Prompts 等能力（经实际使用验证后引入）；
-   可选只读数据库分析，例如受限 EXPLAIN；
-   更丰富的真实项目 benchmark；
-   团队级共享或服务化能力；
-   插件生态与社区贡献机制。

以上为路线图候选项，不代表全部承诺进入对应版本。

## 6. 输出契约

### 6.1 总体要求

MCP Tool 以结构化 JSON 数据为主，附带必要的简短解释。Server
不负责生成冗长的最终自然语言报告，Agent 可以基于结构化结果组织回答。

建议统一结果包含：

-   `success`：本次分析是否成功完成；
-   `summary`：简要结果；
-   `findings`：发现列表；
-   `metadata`：分析范围、耗时、分析器版本等；
-   `warnings`：覆盖范围限制、跳过项或不确定性；
-   `errors`：可操作的错误信息（失败时）。

### 6.2 Finding 字段

每条发现尽可能包含：

-   `code`：稳定的规则/发现标识；
-   `severity`：`INFO`、`WARNING`、`ERROR` 等；
-   `title`；
-   `location`：文件、行号、列号或符号位置；无法定位时为空并说明；
-   `evidence`：证据列表；
-   `description`：事实或风险说明；
-   `suggestion`：建议；
-   `confidence`：可选的置信度；
-   `kind`：事实、规则命中或风险推断。

不得把置信度伪装成统计准确率。若无法合理量化，宁可省略该字段。

### 6.3 证据要求

证据应尽可能可复核，并包含来源类型、路径、位置和必要的摘录/标识。敏感配置值必须脱敏。不要为了满足统一结构而虚构行号或证据。

## 7. 安全与权限要求

### 7.1 文件系统

-   用户显式指定或授权 Workspace 根目录；
-   所有路径解析后必须验证仍位于授权根目录内，防止
    `..`、符号链接等路径逃逸；
-   V0.1 只读，不修改目标项目；
-   限制扫描文件类型、文件数量、单文件大小和总扫描规模；
-   默认忽略 `.git`、`target`、`build`、`.idea` 等非必要目录；
-   对 `.env`、凭据文件和配置中的密码、Token、Secret 等敏感值脱敏；
-   不将项目内容上传到外部服务。

### 7.2 数据库

-   默认不连接数据库；
-   用户显式配置并授权后，才考虑只读连接；
-   只允许白名单元数据查询和受限 `EXPLAIN`；
-   禁止任意 SQL、DDL、DML、存储过程和多语句执行；
-   设置查询超时、结果行数限制和脱敏策略；
-   数据库分析能力不属于 V0.1 必须交付项。

### 7.3 MCP 与工具输入

-   对路径、参数、文件类型和资源消耗设置校验；
-   不执行项目中的脚本、构建插件或任意命令来完成静态分析；
-   错误信息不得泄漏密钥或完整敏感配置；
-   对超大或不受支持项目给出明确限制，而不是无限扫描。

## 8. 非功能需求与质量指标

V0.1 必须具备：

-   可重复运行的自动化测试；
-   每个分析器的正例、反例和边界样例；
-   MCP 集成测试，覆盖工具注册、参数校验、调用和结果序列化；
-   至少一个多模块 Spring Boot 真实结构样例；
-   准确性验证：检查命中、漏报、误报和证据位置；
-   性能基准：记录项目规模、扫描耗时和资源消耗；
-   CI 自动构建和测试；
-   文档中的能力边界与已知限制。

不在缺少数据时承诺固定的准确率、QPS
或扫描耗时。先建立可复现基线，再设定阈值。

## 9. 发布与社区要求

首发目标为 B + C： - 可安装、可配置、可在常见 MCP Client 中接入； -
提供最小可运行示例和真实使用案例； - 提供清晰
README、快速开始、配置说明、常见问题和安全说明； - 提供
CONTRIBUTING、Issue/PR 模板、行为准则（如需要）和路线图； -
对外说明当前支持的 JDK、Spring Boot、Spring AI MCP 和构建工具版本； -
采用明确的开源许可证（许可证类型待项目负责人确认）； - 通过 GitHub
Actions 保证基本质量门禁。

长期希望发展为持续维护的 Java
后端工程分析工具，并探索规则与分析器扩展生态。

## 10. V0.1 验收标准

V0.1 是否发布，不以 Tool 数量或代码行数判断。至少满足：

1.  用户能按照文档在本地启动 STDIO MCP Server，并由目标 MCP Client
    成功调用。
2.  用户能指定一个授权项目目录，获得稳定的项目画像。
3.  能识别 Maven 多模块结构并输出模块依赖数据。
4.  Maven 分析能给出依赖冲突/仲裁结果及可复核依赖路径。
5.  Spring Boot 分析能定位配置文件并输出经过测试的配置/组件风险。
6.  MyBatis 分析能识别一组受支持的 Mapper/XML 关系并提取 SQL。
7.  SQL 规则有明确规则说明、正反例和误报边界。
8.  所有结论都遵循证据契约，不伪造位置或确定性。
9.  路径访问、敏感信息脱敏和只读策略有自动化测试。
10. 单元、集成、真实样例和 CI 均可运行。
11. README、快速开始、安全说明、贡献指南和路线图完整。

## 11. 待确认事项

以下事项不应由实现者擅自决定，应在技术设计或首次发布前由项目负责人确认：

-   项目许可证；
-   Spring Boot / Spring AI MCP 的具体稳定兼容版本；
-   最低支持的 JDK 和 Maven 版本；
-   V0.1 各分析器的精确规则清单；
-   Workspace 配置方式及 MCP Client 的配置示例；
-   是否在首发提供预编译发行包；
-   Benchmark 项目来源及许可证；
-   数据库只读分析的后续权限模型。
